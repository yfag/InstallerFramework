# InstallerFramework — Claude Code Project Memory

## What this project is

A .NET 10 / C# 13 CLI tool (`installer.exe`) for deploying ~70 Windows Service and IIS applications to remote servers over WinRM. It replaces manual install scripts and ad-hoc Chocolatey invocations with a declarative YAML-driven workflow.

**GitHub:** https://github.com/yfag/InstallerFramework  
**Current version:** v1.0.8  
**Owner:** Yngve Fagerheim (yngve.fagerheim@sikri.no)

## Architecture

### Two manifest types
- **Application manifests** (`<AppName>.application.yaml`) — what an application is: type, paths, service account, config parameter defaults. Generated by `installer prepare`.
- **Environment manifests** (`<env>.yaml`) — where and how to deploy: servers, parameter overrides, service account.

### Pipeline pattern
Each deployment runs `IDeploymentStep` instances in sequence via `DeploymentOrchestrator`. Steps: ValidateManifest → ResolvePackage → CheckConnectivity → CreateBackup → StopApplication → ExtractPackage → ApplyConfiguration → DeployFiles → RemoveInstallDirectory → RegisterApplication → StartApplication → HealthCheck. On failure, completed steps roll back in reverse via `RollbackAsync`.

### Key types
- `DeploymentContext` — carries all state for one app × one server through the pipeline
- `EnvironmentManifest` / `ApplicationManifest` — YAML-deserialized models (YamlDotNet)
- `IApplicationAdapter` — implemented by `WindowsServiceAdapter` and `IisAdapter`
- `IRemoteExecutor` — implemented by `WinRmExecutor` (production) and `LocalExecutor` (localhost)
- `DeploymentService` — orchestrates multi-app/multi-server runs; contains static helpers used by commands
- `NuGetPackageResolver` — resolves `.nupkg` files from a local directory or UNC share

### Project structure
```
src/
  InstallerFramework.Cli/         ← Entry point, commands, DeploymentService
    Commands/                     ← PrepareCommand, InstallCommand, UninstallCommand,
                                     StatusCommand, DiffCommand, ValidateCommand
    Program.cs                    ← Serilog setup, global --verbose flag, root command wiring
    DeploymentService.cs          ← Orchestration + static helpers
  InstallerFramework.Core/        ← Domain logic, no CLI dependencies
    Adapters/                     ← WindowsServiceAdapter, IisAdapter
    Configuration/                ← ManifestLoader, ManifestGenerator, ManifestValidator,
                                     ConfigurationMerger, ManifestValidator
    Models/                       ← DeploymentContext, EnvironmentManifest, ApplicationManifest, ...
    Packages/                     ← NuGetPackageResolver
    Pipeline/Steps/               ← One file per pipeline step
    Remote/                       ← WinRmExecutor, LocalExecutor
```

## Key design decisions and conventions

### EffectiveInstallDirectory
`DeploymentContext.EffectiveInstallDirectory` is the single source of truth for install path inside pipeline steps and adapters. It checks `Deployment.InstallDirectoryOverride` first, then falls back to `Service.InstallDirectory` or `Iis.PhysicalPath` from the manifest. **Never read the manifest path directly in a step — always use this property.**

For commands that work outside a DeploymentContext (DiffCommand, StatusCommand, DeploymentService pre-checks), use the `DeploymentService.ResolveEffectiveInstallDirectory(appManifest, deployment)` static helper instead.

### EffectiveIisApplicationPath
Same pattern for IIS virtual path: `DeploymentContext.EffectiveIisApplicationPath` checks `Deployment.ApplicationNameOverride` first.

### Version resolution order
1. `version:` in the deployment block (env manifest)
2. `version:` in the application manifest (set by `installer prepare`)
3. Error

### Logging / verbosity
- Serilog is configured in `Program.cs` before command parsing (pre-scan args for `--verbose`/`-v`)
- Console: `Warning` level by default, `Information` when `--verbose`
- Log files: always written at `Debug` level to `log/<timestamp>.log` next to the exe
- The summary table (Spectre.Console) is always shown regardless of verbosity

### Service accounts (three-level resolution)
1. Per-app override: `account:` inside `service:` or `app-pool:` in app manifest
2. Environment default: `domain-account.account` in env manifest
3. Built-in fallback: `LocalSystem` (services) / `ApplicationPoolIdentity` (IIS)

gMSA accounts end with `$` — no password needed. Regular domain accounts prompt once.

### Runtime preservation (IIS, `installer prepare`)
When re-running `prepare` without `--overwrite`, if an existing manifest is found for an IIS app, its `runtime` field (Core/Framework) is read and written back after fresh generation. This preserves manual runtime corrections. See `PrepareCommand.cs`.

## GitHub Actions / CI

Workflow: `.github/workflows/build.yml`
- Triggers: push to `main`, push of `v*` tags
- On `v*` tag: publishes self-contained `win-x64` exe, creates GitHub Release with auto-generated notes
- Requires `permissions: contents: write` at the job level

**To release a new version:** first commit and push a version bump so the repo always reflects the tag — `<Version>` in `InstallerFramework.Cli.csproj`, plus "Current version" and the "as of" heading in this file — then tag that commit:
```bash
git tag v1.0.X
git push origin main --tags
```
GitHub Actions builds and publishes the release automatically. The exe's version comes from the tag (CI passes `-p:Version`), so the csproj default only matters for local builds.

## Known friction: git lock files

The repo lives on a Windows NTFS mount. The Linux sandbox **cannot delete** `.git/*.lock` files — `Operation not permitted`. This means every git operation leaves stale lock files behind.

**Claude Code has permission to fix this automatically** by running the equivalent of:
```powershell
Remove-Item 'C:\<repo-path>\InstallerFramework\.git\index.lock' -Force -ErrorAction SilentlyContinue
Remove-Item 'C:\<repo-path>\InstallerFramework\.git\HEAD.lock' -Force -ErrorAction SilentlyContinue
```
...before retrying any failing git command. The actual path can be found from `git rev-parse --show-toplevel` run locally, or it's wherever the user has cloned the repo.

Also: close VS Code / GitHub Desktop / any Git GUI before git operations to prevent new locks being created mid-command.

## Environment manifest optional fields (recent additions)

```yaml
deployments:
  - application: Elements.ConfigServer
    application-name-override: ConfigServer     # Override IIS virtual path (IIS only)
    install-directory-override: E:\MyApps\Svc   # Override install dir / physical path (any type)
    version: 2.1.0                              # Pin version for this environment only
    servers:
      - SERVER-01
```

## What's been built and working (as of v1.0.8)

- Full deploy pipeline with rollback
- Windows Service and IIS application support
- gMSA and domain account support (with SeServiceLogonRight auto-grant)
- NuGet package resolution from local/UNC paths
- `prepare` — scans packages, generates manifests, preserves IIS runtime on re-run
- `install`, `uninstall`, `status`, `diff`, `validate` commands
- `--verbose` / quiet mode with timestamped log files
- `application-name-override` — override IIS virtual path per deployment
- `install-directory-override` — override install directory per deployment
- GitHub Actions build + release pipeline
- README fully documenting all features
