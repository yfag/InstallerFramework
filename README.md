# InstallerFramework

A command-line tool for deploying Windows Service and IIS applications to remote servers over WinRM. Replaces manual install scripts, CSV-driven update procedures, and ad-hoc Chocolatey invocations with a single, declarative workflow driven by YAML manifest files.

## Overview

InstallerFramework reads two kinds of YAML files:

- **Application manifests** (`<AppName>.application.yaml`) — describe *what* an application is: its type (Windows Service or IIS), install paths, service account override, and configuration parameter defaults extracted from the package. One file per application, version-controlled alongside the application.
- **Environment manifests** (`<environment>.yaml`) — describe *where* and *how* to deploy: which servers, which applications, shared parameter values, and the default service account. One file per environment (e.g. `production.yaml`, `test.yaml`).

At deploy time the tool merges these two sources, connects to each target server over WinRM, and runs a pipeline of steps: validate → resolve package → check connectivity → backup → stop → extract → configure → register → start → health check.  If any step fails, completed steps are automatically rolled back.

---

## Prerequisites

**On the deployment machine (where you run `installer.exe`):**
- Windows, with network access to the target servers
- Read access to the package source directory (UNC share or local path)
- Domain credentials if deploying to domain-joined servers

**On each target server:**
- WinRM enabled and accessible (`winrm quickconfig`)
- PowerShell 5.1 or later, 7.0 or later recommended
- .NET Core 10 (latest version recommended)
- IIS with the WebAdministration module installed (for IIS applications only)

Deploying the OnPrem.Infrastructure.Deploy will resolve these prerequisites.

## Bundle structure

A typical deployment bundle looks like this:

```
MyBundle\
│
├── ChocoPackages\                    ← NuGet packages (.nupkg files)
│   ├── MyWebApp.3.1.0.nupkg
│   ├── MyService.2.4.1.nupkg
│   └── ...
│
├── manifests\                        ← Generated by 'installer prepare'
│   ├── MyWebApp.application.yaml
│   ├── MyService.application.yaml
│   └── ...
│
├── deployment-template.yaml          ← Deployment scaffold (generated by 'installer prepare')
├── production.yaml                   ← Environment manifest
└── test.yaml                         ← Another environment manifest
```

## Workflow

### First-time setup

Run this sequence once when setting up a new bundle or onboarding a new set of applications.

**Step 1 — Generate application manifests**

```powershell
installer.exe prepare --source .\ChocoPackages
```

This scans every `.nupkg` in the `ChocoPackages` folder, detects whether each is a Windows Service or IIS application, extracts configuration keys and their default values from the package's `appsettings.json`, and writes one `.application.yaml` per package to `.\manifests\`.

It also generates `deployment-template.yaml` at the bundle root — a ready-to-paste scaffold for the `deployments:` section of your environment manifest.

**Step 2 — Review the generated application manifests**

Open each `.application.yaml` and fill in any blank fields:

- `service.display-name` and `service.description`
- `service.install-directory` or `iis.physical-path`
- `iis.site-name` and `iis.application-path` (IIS only)

Everything else — version, type, app pool settings, and parameter defaults — is already populated from the package.

**Step 3 — Create an environment manifest**

Create `production.yaml` (or copy an existing one). Copy the deployment entries from `deployment-template.yaml` into its `deployments:` section. Then fill in:

- Server names for each application
- The default service account (`domain-account.account`)
- Any parameter values that need to differ from the app-manifest defaults

See [Environment manifest](#environment-manifest) for the full structure.

**Step 4 — Validate**

```powershell
installer.exe validate --env .\production.yaml
```

Checks all manifests for consistency without touching any server. Fix any reported errors before proceeding.

**Step 5 — Preview**

```powershell
installer.exe diff --env .\production.yaml
```

Shows what `install` would do: which applications would be installed fresh, which would be updated, and which are already at the correct version. Also checks whether every package file is present.

**Step 6 — Deploy**

```powershell
installer.exe install --env .\production.yaml
```

Connects to each server over WinRM and runs the deployment pipeline for every application that is not already at the correct version.

### Day-to-day: updating applications

When a new version of one or more applications arrives:

**Single application update:**

```powershell
# 1. Regenerate the manifest for the new package
installer.exe prepare --source .\ChocoPackages --package MyWebApp

# 2. Preview the change
installer.exe diff --env .\production.yaml --app MyWebApp

# 3. Deploy
installer.exe install --env .\production.yaml --app MyWebApp
```

**Full bundle update:**

```powershell
installer.exe prepare --source .\ChocoPackages --overwrite
installer.exe diff    --env .\production.yaml
installer.exe install --env .\production.yaml
```

> **Note:** `installer prepare` writes the detected package version directly into each `.application.yaml`. No manual version editing is needed in the environment manifest — the version travels with the manifest file.
>
> If you need to pin a specific version for a particular environment (e.g. keep production on an older version while test gets the new one), add a `version:` field to that deployment's entry in the environment manifest. It takes precedence over the application manifest version.

## Manifest files

### Environment manifest

Controls where and how applications are deployed. One file per environment.

```yaml
environment:
  name: Production

  # Where the .application.yaml files are located.
  # Relative to this file, or absolute.
  manifests-path: ./manifests

  # Default package source — can be overridden per application.
  default-package-source: \\fileserver\packages\MyBundle\ChocoPackages

  # Backup settings
  backup-root: C:\InstallBackups
  backup-retention-days: 7

  # Default service account for all applications in this environment.
  # Individual applications can override this with their own 'account:' field.
  # Omit the entire block to use built-in accounts (LocalSystem / ApplicationPoolIdentity).
  domain-account:
    account: DOMAIN\svc-elements$   # gMSA — no password needed (trailing $)
    # account: DOMAIN\svc-elements  # Regular domain account — installer will prompt for password

  # Parameter values shared across all applications.
  # These are merged with each deployment's own parameters;
  # deployment-specific values take precedence.
  shared-parameters:
    "AppSettings:ConfigServer.BaseUrl": "https://configserver.prod.example.com"
    "AppSettings:ConfigServer.Scopes": "PROD"
    "Environment:Name": "prod"

  deployments:

    - application: MyWebApp
      # version: 3.1.0   # Optional — overrides the version in the application manifest
      servers:
        - WEB-SERVER-01
        - WEB-SERVER-02
      parameters:
        # Only values that differ from the application manifest defaults
        "AppSettings:SomeKey": "production-specific-value"
      health-check:
        url: "https://WEB-SERVER-01/MyWebApp/api/version"
        timeout-seconds: 30
        retry-count: 5
        retry-interval-seconds: 5
        expected-status: "200"

    - application: MyService
      servers:
        - APP-SERVER-01
      # health-check:   # Windows Services typically don't expose HTTP health endpoints
```

#### Version resolution

The version to deploy is resolved in this order:

1. `version:` in the deployment block (environment manifest) — use this to pin a specific version per environment
2. `version:` in the application manifest — set automatically by `installer prepare`
3. Error if neither is set

#### Parameter resolution

Parameters are merged in three levels (lowest to highest priority):

1. Application manifest `parameters:` — defaults extracted from the package's `appsettings.json`
2. Environment manifest `shared-parameters:` — values common to all applications in this environment
3. Deployment block `parameters:` — values specific to this application in this environment

Only parameters that genuinely differ from the defaults need to be specified in the environment manifest.

### Application manifest

Describes a single application. Generated by `installer prepare` and version-controlled alongside the deployment bundle.

```yaml
# MyWebApp.application.yaml

application:
  name: MyWebApp
  version: 3.1.0          # Set by 'installer prepare'; override per-environment in environment manifest
  type: iis-application   # or: windows-service

  package:
    id: MyWebApp
    # source: \\fileserver\packages  # Optional: override package source for this app only
    # content-path: tools            # Default — no need to change for standard packages

  # For IIS applications:
  iis:
    site-name: Default Web Site
    application-path: /MyWebApp
    physical-path: C:\inetpub\wwwroot\MyWebApp
    runtime: Core           # Core (ASP.NET Core) or Framework (.NET Framework 4.x)
    app-pool:
      name: MyWebApp
      pipeline-mode: Integrated
      # account:            # Optional: overrides environment default (domain-account.account)
      idle-timeout-minutes: 0
      auto-start: true
      start-mode: AlwaysRunning

  # For Windows Services:
  service:
    name: MyService
    display-name: "My Background Service"
    description: "Processes incoming messages from the queue."
    start-type: automatic-delayed   # automatic-delayed | automatic | manual | disabled
    # account:                      # Optional: overrides environment default (domain-account.account)
    install-directory: C:\Program Files\MyService
    # binary-path-suffix: --environment Production   # Optional suffix added to sc.exe binary path

  configuration:
    # Default values extracted from the package's appsettings.json.
    # Override any of these in the environment manifest's shared-parameters or deployment parameters.
    parameters:
      "AppSettings:ConfigServer.BaseUrl": "https://configserver.dev.example.com"
      "AppSettings:SomeKey": "default-value"
      "Logging:LogLevel:Default": "Warning"
```

## Command reference

All commands accept `--help` for full option descriptions.

---

### `prepare`

Scans a package directory and generates application manifests.

```
installer.exe prepare --source <path> [options]
```

| Option | Short | Description |
|---|---|---|
| `--source <path>` | `-s` | **Required.** Path to the `ChocoPackages` directory. |
| `--out <path>` | `-o` | Output directory for manifests. Defaults to `../manifests` relative to `--source`. |
| `--package <id>` | `-p` | Generate for one package only. Omit to process all packages. |
| `--overwrite` | | Overwrite existing manifest files. Without this, existing files are skipped. |

**Outputs:**
- One `<AppName>.application.yaml` per package in the output directory
- `deployment-template.yaml` at the bundle root (only when no `--package` filter is used)

---

### `install`

Deploys applications to target servers.

```
installer.exe install --env <file> [options]
```

| Option | Short | Description |
|---|---|---|
| `--env <file>` | `-e` | **Required.** Path to the environment manifest. |
| `--app <name>` | `-a` | Deploy this application only. |
| `--server <name>` | `-s` | Deploy to this server only. |
| `--force` | `-f` | Redeploy even if the correct version is already installed. |
| `--dry-run` | | Validate manifests only — no server connections, no changes. |
| `--password <pw>` | `-p` | Domain account password. Also accepted via `INSTALLER_DOMAIN_PASSWORD` environment variable. Prompted interactively if not supplied. |
| `--no-rollback` | | Leave the server in its current state on failure (useful for diagnosing startup errors). |

**Deployment pipeline (per application × per server):**

1. Validate manifest
2. Resolve package file
3. Check connectivity & detect installed version
4. Create backup of existing installation
5. Stop the service / take the IIS app offline
6. Extract package to staging directory
7. Apply configuration (merge parameters into `appsettings.json`)
8. Deploy files to install directory
9. Register service or IIS application
10. Start the service / bring IIS app online
11. Run health check (if configured)

Steps are run in sequence. On failure, all completed steps are rolled back in reverse order (unless `--no-rollback` is set).

**Skip logic:** If a server already has the target version installed (detected via an admin share read before opening WinRM), the entire pipeline is skipped for that server. Use `--force` to override this.

---

### `uninstall`

Removes applications from target servers, including all files and the service/IIS registration.

```
installer.exe uninstall --env <file> --app <name> [options]
installer.exe uninstall --env <file> --all [options]
```

| Option | Short | Description |
|---|---|---|
| `--env <file>` | `-e` | **Required.** Path to the environment manifest. |
| `--app <name>` | `-a` | Uninstall this application. Mutually exclusive with `--all`. |
| `--all` | | Uninstall every application in the environment manifest. |
| `--server <name>` | `-s` | Uninstall from this server only. |

A confirmation prompt is shown before any changes are made.

---

### `status`

Shows the running state and installed version of each application on its configured servers.

```
installer.exe status --env <file> [options]
```

| Option | Short | Description |
|---|---|---|
| `--env <file>` | `-e` | **Required.** Path to the environment manifest. |
| `--app <name>` | `-a` | Show status for this application only. |
| `--server <name>` | `-s` | Show status for this server only. |

Displays a table with Target Version, Installed Version, and running state (Running / Stopped / Not Installed).

---

### `diff`

Shows what `install` would do without making any changes. Reads server state over WinRM.

```
installer.exe diff --env <file> [options]
```

| Option | Short | Description |
|---|---|---|
| `--env <file>` | `-e` | **Required.** Path to the environment manifest. |
| `--app <name>` | `-a` | Show diff for this application only. |

For each application/server pair, reports one of:

| Action | Meaning |
|---|---|
| **Install (new)** | Not currently installed — will be deployed fresh |
| **Update** | Installed at a different version — will be updated |
| **Up to date** | Already at the target version — will be skipped |
| **Error** | Could not connect to the server |

Also checks whether the target package file exists in the package source.

---

### `validate`

Validates all manifests for consistency without connecting to any server.

```
installer.exe validate --env <file>
```

Checks that:
- All applications referenced in the environment manifest have a corresponding `.application.yaml`
- All applications have a resolvable version
- All `required-parameters` (legacy) are satisfied
- Service and IIS configuration blocks are complete
- No conflicting configuration mode settings

Exit code 0 = valid. Exit code 1 = one or more errors.

## Configuration modes

After extracting a package, the installer applies environment-specific values to `appsettings.json`. Three modes are available, configured per-application in the application manifest.

### Merge mode (default)

The package's own `appsettings.json` is used as the base. Deployment parameters are overlaid on top. Keys not listed in any parameters block keep their original package values.

This is the recommended mode and the default when `installer prepare` generates manifests. No template file is needed, and values that don't vary between environments never need to be mentioned in any manifest.

```yaml
configuration:
  parameters:
    "AppSettings:Environment": "Production"   # only override what actually differs
```

### Overlay mode

Generates a minimal `appsettings.<Suffix>.json` containing only the deployment parameters. ASP.NET Core layered configuration merges this over the base `appsettings.json` at runtime.

```yaml
configuration:
  overlay-suffix: Production    # produces appsettings.Production.json
  parameters:
    "AppSettings:Environment": "Production"
```

### Template mode

Replaces `{{Token}}` placeholders in a template file with deployment parameter values, producing `appsettings.json`. All tokens in the template must be resolved.

```yaml
configuration:
  template: appsettings.template.json
  parameters:
    ConfigServerUrl: "https://configserver.prod.example.com"
    ConfigServerPassword: "..."
```

## Service accounts

Applications run under a service account configured at three levels (first match wins):

1. **Per-application override** — `account:` field inside the `service:` or `app-pool:` block in the application manifest
2. **Environment default** — `domain-account.account` in the environment manifest
3. **Built-in fallback** — `LocalSystem` for Windows Services, `ApplicationPoolIdentity` for IIS

### Group Managed Service Accounts (gMSA)

Accounts whose name ends with `$` are treated as gMSA accounts. No password is needed — Active Directory manages the secret automatically.

```yaml
domain-account:
  account: DOMAIN\svc-elements$
```

### Regular domain accounts

Accounts without a trailing `$` require a password. The installer collects it once per unique account name before any server-side changes begin.

The password can be supplied via:
1. `--password` flag (command line)
2. `INSTALLER_DOMAIN_PASSWORD` environment variable
3. Interactive prompt (if neither of the above is provided)

If different applications use different domain accounts, the installer will prompt separately for each.

## Health checks

An optional health check can be configured per deployment. After the application starts, the installer polls a URL and waits for the expected HTTP status code before declaring success.

```yaml
deployments:
  - application: MyWebApp
    health-check:
      url: "https://WEB-SERVER-01/MyWebApp/api/version"
      timeout-seconds: 30       # Wait up to 30 seconds per attempt
      retry-count: 5            # Try up to 5 times
      retry-interval-seconds: 5 # Wait 5 seconds between retries
      expected-status: "200"    # Accept HTTP 200 as healthy
```

If the health check fails after all retries, the deployment is marked as failed and the pipeline rolls back.

Windows Services typically do not expose HTTP endpoints — omit the `health-check` block for those.

## Rollback behaviour

When a deployment step fails, the orchestrator runs the `RollbackAsync` method of each previously completed step in reverse order. This restores the server to its pre-deployment state:

- The backup is restored to the install directory
- The previous service registration or IIS configuration is reinstated
- The service or application pool is restarted

**`--no-rollback`** disables this behaviour and leaves the server in whatever state it reached at the point of failure. Use this when diagnosing a problem — for example, to inspect the extracted package files or a partially applied configuration — before manually retrying or rolling back.
